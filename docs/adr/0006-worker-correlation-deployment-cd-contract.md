# ADR-0006 — Worker-side correlation propagation & deployment/CD contract (WP0.2-B, Checkpoint B)

**Status:** Accepted (merge of the WP0.2-B Checkpoint B pull request is the acceptance gate)
**Date:** 2026-10-04
**Decision register:** D-050
**Scope:** (A) propagating a TapJob correlation id across Celery message boundaries and binding it
(plus Celery's own task identity) into structured worker logs; (B) the deployment/CD contract for
promoting a single, immutable backend image through staging to production. No real deploy, no
GHCR publish, no EasyPanel/Cloudflare/server mutation happens in this checkpoint or pull request.
No product feature, no domain model, no database migration is added. `MatchingEngine` remains
outside the port set (ADR-0005); nothing here changes that.

## Context

`docs/IMPLEMENTATION_PLAN.md` WP0.2-B names Checkpoint B as "worker-side request correlation;
deployment/CD contract (ADR-0006, not a real deploy)" — the second and final checkpoint of WP0.2-B,
authorized only after Checkpoint A (internal ports/capability model) was independently verified and
merged (PR #12/#13, `main` commit `a8bfbe621e5a83ae5f205adb1919ce3250684efb`).

HTTP already has a correlation convention (ADR-0002, ADR-0004): `X-Request-ID` is validated/
generated by `RequestContextMiddleware`, bound into `tapjob_api.core.logging.request_id_var`, and
echoed into every structured log line and the response header. Nothing propagated that identity (or
any equivalent) into the worker; a Celery task's logs carried no way to relate back to whatever
HTTP request (if any) caused it, nor to distinguish one task execution from the broader workflow it
belongs to.

Separately, `docs/ARCHITECTURE.md` §11/§14 and `docs/FOUNDATION_DECISIONS.md` §2 already commit to a
topology (owner's Linux server, Docker Compose, Cloudflare Tunnel ingress, EasyPanel as an
operations UI only) and a backend-image strategy (D-043: one image for `api`/`worker`/`migrate`),
but no PR yet turned those into an actual, reviewable deployment/CD contract: how an image gets
built, how its identity is pinned, in what order services come up, how rollback works, what
EasyPanel/Cloudflare are and are not allowed to own.

## Decisions — Part A: worker correlation

### A1. Three identifiers, never conflated

- **HTTP request id** — one HTTP request (`tapjob_api.http.request_context`, unchanged).
- **TapJob correlation id** (new, this ADR) — connects a request or other logical origin to
  whatever asynchronous work it causes, across any number of tasks, retries or fan-out.
- **Celery task id** (`Task.request.id`) — one specific execution attempt of one task.

Celery's own built-in message `correlation_id` property is deliberately **not** reused for the
second concept: per Celery's own documentation (Task Request reference, consulted 2026-10-04), it
is "usually the same as the task id" — a different, lower-level AMQP/task-identity concept, not a
cross-task-boundary application correlation id. A conflated reuse would have made "the same
correlation id across a whole workflow" and "this one task's own identity" indistinguishable.
TapJob's correlation id instead travels in its own custom Celery message header,
`tapjob_worker.correlation.CORRELATION_HEADER_NAME` = `"tapjob_correlation_id"`.

### A2. One shared validation policy, two justified fallbacks

`tapjob_api.core.correlation.CORRELATION_ID_PATTERN`/`resolve_correlation_id` is the single bounded,
log-injection-safe policy (`^[A-Za-z0-9._-]{1,128}$`) both HTTP and the worker apply to an inbound
identifier — extracted from `tapjob_api.http.request_context`'s pre-existing, identical regex
(`docs/ENGINEERING_STANDARDS.md` §1: one source of truth per concern) rather than letting the
worker grow a second, potentially-divergent copy. Callers differ only in their fallback when the
candidate is absent or invalid:

- HTTP mints a fresh random id (`uuid4().hex`, unchanged behavior).
- The worker prefers a **deterministic, already-stable identity** — the task's own `root_id`
  (stable across an entire workflow/retry chain, always present, never freshly randomized) — over
  inventing a random one, since a task already carries a stable identity even with no inbound
  header (e.g. a Celery Beat/periodic task with no HTTP or parent-task origin).

### A3. Propagation: `before_task_publish`, confirmed against Celery's own signal reference

Investigated directly against Celery's official documentation (Signals reference, consulted
2026-10-04) before committing to this mechanism: `before_task_publish` receives a mutable `headers`
mapping ("Application headers mapping (can be modified)"), dispatched for every task publish
regardless of where in the codebase `.delay()`/`.apply_async()` is called — exactly the
"works for any future task without each feature remembering to propagate a header" requirement.
`tapjob_worker.correlation._before_task_publish` reads the current
`tapjob_api.core.logging.request_id_var` (set either by the HTTP middleware, or by this module's
own `task_prerun` hook for a task already executing) and, if present, injects it into `headers`
**unless the caller already set that header explicitly** — an explicit value is never silently
overwritten. With no TapJob context active, no header is added at all; nothing invents a
correlation id at publish time. Because `task_prerun` (A4) binds `request_id_var` before a task
body runs, a task publishing a *nested* task from within its own body automatically propagates the
same correlation id forward — no extra code needed at each call site.

### A4. Consumption: `task_prerun` binds, three signals reset

`task_prerun` extracts the header, resolves it via A2's shared policy (falling back to `root_id`),
and binds both `request_id_var` (the resolved correlation id) and a second, generic
`tapjob_api.core.logging.task_context_var` (Celery task id, root id, parent id, task name, retry
count — never task `args`/`kwargs`, which may carry sensitive data,
`docs/ENGINEERING_STANDARDS.md` §18). `task_context_var` is a small, intentionally generic addition
to `tapjob_api.core.logging` (not Celery-specific there — the worker decides what it holds), merged
into every JSON log line the same way `request_id_var` already is, so a task's *own* log statements
during its body automatically carry this metadata, not just the hook's own log lines.

Three signals reset state, not one: `task_postrun` (the normal path), plus `task_failure` and
`task_retry` as a defensive backstop. Celery's own signal documentation describes `task_postrun` as
"dispatched after a task has been executed" without an explicit, documented guarantee that it also
fires on every failure/retry path across all Celery versions/pools — rather than depend on an
unverified assumption for a cleanup-correctness invariant, all three call the same idempotent
`_reset_context`, so there is no path left where a finished task's context survives into whatever
this worker process/thread executes next. This is deliberately scoped to the **prefork/solo pool
model** (the default, and what TapJob's Compose/Dockerfile configuration actually runs): one task
body executes at a time per OS thread/process, so a given task's `task_prerun`/`task_postrun` pair
always fully brackets its own execution with no interleaving from a second, concurrently-executing
task's hooks on the same thread. This is **not** re-verified for cooperative pools
(eventlet/gevent), which TapJob does not use.

### A5. Signal connection is idempotent, same pattern as the existing `setup_logging` hook

`connect_correlation_signals()` connects all five signal handlers with an explicit `dispatch_uid`
each — the identical mechanism `services/worker/src/tapjob_worker/celery_app.py` already relies on
for its pre-existing `setup_logging` connection. Celery's dispatcher treats a repeat `.connect()`
call with the same `dispatch_uid` as a no-op, so `create_celery_app()` being called more than once
(already true in the test suite) never registers a duplicate handler or causes a duplicate log
event — tested directly (`services/worker/tests/test_correlation.py`) by asserting a second/third
call adds zero additional signal receivers relative to the first.

### A6. Rejected alternatives

- **A custom `Task`/`Request` subclass:** Celery's own `before_task_publish`/`task_prerun`/
  `task_postrun`/`task_failure`/`task_retry` signals already solve this without subclassing
  anything Celery provides; a custom class would be strictly more code for no behavioral gain, and
  harder for a future task to opt out of by accident.
- **Reusing Celery's built-in `correlation_id` message property:** rejected per A1 — it is already
  a different concept with its own default semantics ("usually the same as the task id").
- **A second, divergent request-id validation regex for the worker:** rejected per A2 — extracted
  the one existing policy into `tapjob_api.core.correlation` instead.
- **Randomly generating a correlation id when none is propagated:** rejected — a task's own
  `root_id` is already a stable, available identity; inventing a second, random one when a
  perfectly good deterministic one exists would make retries of the *same* task harder to
  correlate across attempts, not easier.

## Decisions — Part B: deployment/CD contract

### B1. Topology unchanged

This ADR does not redesign infrastructure: owner's Linux server, Docker Compose, PostgreSQL,
Redis, Cloudflare Tunnel/edge, Cloudflare R2 (once storage is needed), EasyPanel as an
operations/deployment UI only, GitHub as the canonical source, GitHub Actions for CI/CD, no
Kubernetes — exactly `docs/ARCHITECTURE.md` §11 and `docs/FOUNDATION_DECISIONS.md` §2.

### B2. Build once, promote the same artifact

```text
commit reviewed -> CI -> build backend image ONCE -> push to GHCR -> immutable digest
  -> staging (same digest) -> verification -> production (same digest)
```

Never: `git pull` + `docker build` on the server; never `:latest` as a release identity; never a
different build per environment. The **unit of promotion is an immutable image digest**
(`registry/repository@sha256:<64 hex>`), not a tag — a commit-SHA tag may exist for human
discovery (`.github/workflows/release-image.yml`'s `docker/metadata-action` step), but it is never
what a deploy references.

**Rejected:** rebuilding per environment (defeats "what was tested in staging is what ships to
production"); `:latest` as the canonical reference (mutable — the same tag can point at a
different image tomorrow, defeating reproducibility and auditability of what is actually running).

### B3. One backend image (D-043 preserved)

`infra/docker/backend.Dockerfile` is unchanged by this checkpoint: it already produces the one
image `api`, `worker` and `migrate` all run, differing only by `command:`/entrypoint — this ADR
does not introduce a second build or a per-service image.

### B4. GHCR contract, not executed in this checkpoint

`.github/workflows/release-image.yml` (new, **`workflow_dispatch`-only** — no `push`/
`pull_request` trigger, so it cannot run as a side effect of any commit, including this one; **no
free-form `ref` input either**, 2026 review, Finding 1A) always builds whatever commit is at the
tip of `main` at run time. A `preflight` job runs first and hard-fails — never silently skips — if
triggered against any ref other than `refs/heads/main`, since `workflow_dispatch` can be triggered
via the GitHub API against any ref containing this workflow file, not just through the Actions UI;
UI/operator discipline alone was not treated as sufficient. That same `preflight` job captures
`ACTUAL_SOURCE_SHA` from the checked-out working tree itself (`git rev-parse HEAD`, Finding 1B) —
never implicit Action context like `github.sha` independently — and uses it explicitly for the
commit tag, the `org.opencontainers.image.source`/`.revision` OCI labels, and the step summary, so
none of those can diverge from what was actually checked out; the `build-and-push` job re-confirms
its own checkout resolves to that same captured SHA before proceeding, as defense in depth. Before
any build step runs, `preflight` also proves the **exact commit SHA about to be built** already had
its own CI run (`.github/workflows/ci.yml`, `event=push`) complete with conclusion `success` —
never "main is green right now" (Finding 1C; the real incident this guards: PR #13 merged cleanly,
but a later post-merge audit-gate failure on a subsequent commit on `main` was discovered only
afterward — "main is green at this moment" never implied this specific commit's own run had
succeeded). That check's pure evaluation logic lives in `tools/deploy/require_ci_success.mjs`
(`evaluateCiRequirement`, mirroring `tools/security/audit-gate.mjs`'s evaluate-then-fetch split)
and is fully unit-tested (`tools/deploy/require_ci_success.test.mjs`, 13 tests covering no-match,
success, failure, in-progress, re-run-after-failure, regression-after-success, out-of-order runs,
and malformed inputs) without ever executing this release workflow. `preflight` uses only
`actions: read` (to query past CI runs via `gh api`) plus `contents: read` — no PAT, no write
permission.

`build-and-push` then builds `infra/docker/backend.Dockerfile` with `docker/build-push-action`,
tags the result from `ACTUAL_SOURCE_SHA` (not implicit git-context detection) plus OCI labels
(title/description/source/revision), pushes to `ghcr.io/<owner>/tapjob-backend`, and captures the
build action's own `digest` output into the run's step summary as the actual promotion reference
(both the full `name@sha256:...` reference and the bare `sha256:...` digest `BACKEND_IMAGE_DIGEST`
expects, B5/B6). Authentication uses `GITHUB_TOKEN` scoped to `packages: write`/`contents: read`
for that one job only — no PAT is created or stored. Third-party actions are pinned by full commit
SHA (`docker/login-action@dbcb81...` v4.6.0, `docker/setup-buildx-action@f87e59...` v4.4.1,
`docker/metadata-action@dc8028...` v6.2.0, `docker/build-push-action@c3c9e2...` v7.4.0), matching
this repository's existing pinning convention (`.github/workflows/ci.yml`). **This workflow has not
been run by this checkpoint** — it exists as a reviewable, inert artifact; running it (and thereby
actually publishing to GHCR) is a separate, later operator action, outside this PR's scope.

PR CI (`.github/workflows/ci.yml`'s new `deploy-contract` job) validates the deployment contract
itself — the image-reference/digest validators (B6), the release CI-success-gate logic, and the
deploy Compose file (B5) — without ever building for or pushing to GHCR, and without ever calling
the real GitHub API; the pre-existing `docker` job already builds/smoke-tests the local dev image
via `infra/compose.yaml`, unchanged.

### B5. Deploy Compose contract

`infra/compose.deploy.yaml` (new) is the versioned, reproducible representation of the runtime
deployment — distinct from `infra/compose.yaml` (local development, still builds the image
locally; unchanged). `api`, `worker` and `migrate` all reference one YAML anchor (`x-backend`)
whose image is `ghcr.io/ricardoo081/tapjob-backend@${BACKEND_IMAGE_DIGEST}` — the canonical
repository is a **fixed literal in the file**, not interpolated from an environment variable, and
`BACKEND_IMAGE_DIGEST` supplies only a bare `sha256:<digest>` with no repository or tag slot at all
(2026 review, Finding 1 of that round: the originally-designed `${BACKEND_IMAGE}` free-form
variable let an operator set a mutable tag or a foreign repository directly, which made the
validator in B6 a convention an operator could simply skip rather than a structural guarantee —
fixing the repository and narrowing the variable to a bare digest removes that gap at the file
level, not just at the validator level). There is **no `build:` directive at all** in this file —
staging/production never build the backend locally. PostgreSQL/Redis publish no host port (the
local dev file still does, for developer convenience; the deploy file never does — these are
reachable only from other services on the Compose network). `api` likewise publishes no host port:
public ingress is Cloudflare Tunnel only (B13), never a directly-exposed container port.
Environment-specific values (`APP_ENV`, `DATABASE_URL`, `REDIS_URL`, `POSTGRES_*`, `SENTRY_DSN`)
come from an `--env-file` supplied at deploy time, never embedded in the committed file (B14).
Validated with `docker compose -f infra/compose.deploy.yaml config` against synthetic-only values
in CI (never a real secret) — this resolves/validates the YAML and env substitution without
pulling or running the referenced image, and a dedicated CI step additionally confirms the
resolved image string is exactly the fixed canonical repository at the given digest.

### B6. Immutable-digest validation

`tools/deploy/validate_image_ref.mjs` (new, zero-dependency, mirrors
`tools/security/audit-gate.mjs`'s existing style) exports two validators: `validateImageRef`
accepts a full `<name>@sha256:<64 lowercase hex characters>` reference (used where a full
reference is still the relevant shape, e.g. a release's own promotion reference), rejecting a bare
`:latest` tag, any other mutable tag with no digest, a tag combined with a digest, a malformed/
short/uppercase-hex digest, or an empty/non-string value; `validateImageDigest` (2026 review,
Finding 2) accepts only the bare `sha256:<64 lowercase hex characters>` form `BACKEND_IMAGE_DIGEST`
actually holds — no repository, no `@`, no tag — rejecting everything `validateImageRef` rejects
plus any full reference (a repository, foreign or canonical, has no slot to occupy in this
variable at all). Neither implements the full OCI reference grammar — a small, auditable allowlist
of the one shape each context actually needs, per the same "small, deterministic, auditable"
design principle `docs/adr/0007`/`0008`'s audit gate already established. 25 deterministic unit
tests (`tools/deploy/validate_image_ref.test.mjs`) plus CI steps (`deploy-contract` job) exercising
the real CLI directly against both validators, and a further step confirming `api`/`worker`/
`migrate` all resolve to the identical, fixed-canonical-repository image reference in the rendered
Compose config (not just three independently-correct references that happen to agree).

### B7. Migration ordering

```text
1. pull/resolve the approved immutable image digest
2. migration job runs on that SAME digest
3. migration succeeds
4. api/worker rollout
5. readiness/health verification
```

Enforced structurally in `infra/compose.deploy.yaml`: `api`/`worker` both `depends_on: migrate:
condition: service_completed_successfully`. Alembic migrations remain forward-safe
(expand/contract preferred for any future schema change needing compatibility, per
`docs/ENGINEERING_STANDARDS.md` §23); an application rollback (B8) does **not** imply an automatic
database downgrade — a destructive/incompatible migration blocks promotion and requires a separate,
explicitly reviewed decision, never an automatic `alembic downgrade`. This checkpoint creates no
migration (no product schema exists yet).

### B8. Release / rollback contract

A release record (pipeline run metadata/step summary, not a new database table) captures: source
commit SHA, image digest, target environment, deployment timestamp, previous digest, migration
revision, result. **Rollback of the application is: promote the previous known-good digest** —
never rebuild old code. If a database migration makes that digest's code incompatible with the
current schema, the pipeline must block/warn per this contract rather than attempt an automatic
`alembic downgrade` (B7) — a human makes that call.

### B9. Health/readiness

Unchanged (ADR-0002): `/health` is process/liveness; `/ready` is dependency readiness (PostgreSQL/
Redis). Deployment acceptance requires migration completion, `/ready` reporting healthy, and the
worker responding to `celery inspect ping` (already the local Compose healthcheck,
`infra/compose.deploy.yaml` mirrors it) — not a product smoke test, since no product feature exists
yet.

### B10. Deployment concurrency

`release-image.yml`'s own build job uses `concurrency: group: release-image` so two manual runs
queue rather than race — a static group is sufficient now that every run always targets the same
ref, `main` (Finding 1A); `cancel-in-progress: false` (a build should finish, not be cancelled,
once started). A *future* deploy-to-environment workflow (not built in this
checkpoint — no real deploy happens here) must scope its own concurrency group per environment
(e.g. `deploy-<environment>`), so staging and production can proceed independently while two
concurrent deploys to the *same* environment cannot (confirmed against GitHub's own Actions
concurrency documentation, consulted 2026-10-04).

### B11. Environments

`local` / `staging` / `production`, per `docs/ARCHITECTURE.md` §12 and
`docs/FOUNDATION_DECISIONS.md` §2 — unchanged. Staging and production never share a database,
secrets, or object-storage namespace; the **same image digest** is what is allowed (and expected)
to cross both. Config varies per environment; the artifact does not.

### B12. EasyPanel's role is bounded

EasyPanel may visualize containers, assist operations, and start/restart services per a future
runbook. It is explicitly **not**: a source of truth, the only place holding Compose/env
configuration, a build location, or a place configuration can silently drift from what this
repository documents. `infra/compose.deploy.yaml` plus an environment's `--env-file` (held outside
the repository, per B14) must remain sufficient to reproduce a deployment without any hidden
EasyPanel-only state.

### B13. Cloudflare boundary (documented, not configured)

Cloudflare Tunnel remains the approved public-ingress path (`docs/ARCHITECTURE.md` §2/§11). This
checkpoint does **not** configure a real tunnel, change DNS, or touch any Cloudflare account/
resource — `infra/compose.deploy.yaml`'s `api` service simply publishes no host port, which is the
repository-side half of that boundary; the Cloudflare-side half is explicitly out of scope here and
remains a separate, later operator action.

### B14. Secrets policy

No secret lives in `infra/compose.deploy.yaml`, `.github/workflows/release-image.yml`,
`infra/docker/backend.Dockerfile`, a build arg, or an image label — every environment-specific
value in the deploy Compose file is a required (`:?`), unset-by-default environment variable,
supplied at deploy time via an `--env-file` an operator holds outside this repository. CI validates
the deploy Compose contract with synthetic/dummy values only (`deploy-contract` job); it never
reads or requires a real secret.

### B15. Provenance / supply chain — deliberately deferred

Evaluated official GitHub artifact attestations / OCI provenance (`actions/attest-build-provenance`
and related) against this checkpoint's priority order: (1) immutable digest, (2) reviewed source,
(3) reproducible build, (4) minimal workflow permissions, (5) same-digest promotion. All five are
already satisfied by B2–B8 above without attestations. Adding SBOM/provenance generation now would
be complexity introduced because the tooling exists, not because this checkpoint has an unmet need
for it — deferred, to be reconsidered if/when an actual compliance or supply-chain-risk trigger
requires it (consistent with `docs/FOUNDATION_DECISIONS.md` §9 "cost escalation should be
evidence-driven," applied here to process complexity instead of infrastructure cost).

## Testing implications

- Worker correlation: `services/worker/tests/test_correlation.py` (30 tests) — publish-side
  propagation (within/without context, never overwriting an explicit header, nested-task
  propagation), consumption/binding (valid header, missing-header fallback, invalid-header
  rejection, task-id-vs-correlation-id distinction, root/parent-id preserved separately, args/
  kwargs never captured, no-request-object safety), the untrusted/malformed-metadata hardening
  added in the 2026 review (Finding 3: non-string/wrong-type header, empty/overlong header,
  invalid or non-string `root_id`, invalid `task_id`, both invalid, newline-bearing metadata
  omitted from logged context rather than logged raw), cleanup (success/failure/retry paths all
  clear state, two sequential tasks never share context), and signal-wiring idempotency (relative
  receiver-count deltas, robust to whatever else already ran in the same test session).
- Shared validation policy: `services/api/tests/test_correlation.py` (11 tests) — pattern/fallback
  behavior directly, plus the same review's `object`-typed candidate hardening (int/list/dict/bool
  candidates all fall back without raising); `services/api/tests/test_request_context.py` gains
  one regression test proving an invalid inbound `X-Request-ID` is still regenerated after the
  extraction.
- Structured logging: `services/api/tests/test_logging.py` gains two tests for
  `task_context_var`'s merge behavior (present and absent).
- Deployment contract: `tools/deploy/validate_image_ref.test.mjs` (25 tests — 15 for
  `validateImageRef`, 10 for the `validateImageDigest` form `BACKEND_IMAGE_DIGEST` actually holds,
  2026 review Finding 2, no live registry access) plus `tools/deploy/require_ci_success.test.mjs`
  (13 tests for the release workflow's CI-success-gate logic, Finding 1, no live GitHub API
  access) plus several `deploy-contract` CI steps exercising the real CLIs and the real
  `docker compose config` resolution against synthetic configuration only — each JS test count
  kept separate, never merged into one ambiguous total (2026 review, metadata cleanup).

## Consequences

- `tapjob_api.core.logging` gains one small, generic addition (`task_context_var`) rather than a
  worker-specific concept leaking into a cross-cutting foundation module.
- `tapjob_api.http.request_context` loses its own copy of the request-id regex/resolution function
  in favor of the shared `tapjob_api.core.correlation` module — a mechanical extraction, not a
  behavior change (tested via regression).
- `infra/compose.deploy.yaml` and `.github/workflows/release-image.yml` are new, reviewable
  artifacts; neither is exercised against a real environment by this checkpoint. Checkpoint B
  becomes VERIFIED the same way every prior WP0.2-B checkpoint did (2026 review, Finding 4,
  correcting this ADR's earlier text): implementation → independent review → CI green at the
  latest HEAD → merge → CI green post-merge → independent post-merge verification. The deploy
  contract itself — immutable-digest enforcement, the fixed canonical repository, the release
  workflow's source-SHA/CI-success gates, the correlation propagation — is all verified
  deterministically this way, without publishing an image or promoting an environment. The FIRST
  real execution of `release-image.yml`, and the first real staging/production promotion, is a
  **separate, later, operational gate** — its own explicit authorization, its own credentials/
  environments, its own runbook/checklist — not part of this checkpoint's verification bar.
