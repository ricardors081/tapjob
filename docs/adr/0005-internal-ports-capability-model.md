# ADR-0005 — Internal ports & capability model (WP0.2-B, Checkpoint A)

**Status:** Accepted (merge of the WP0.2-B Checkpoint A pull request is the acceptance gate)
**Date:** 2026-10-02
**Decision register:** D-048
**Scope:** provider-neutral contract foundations for seven ports (`JobSource`, `ResumeParser`, `ResumeRenderer`, `AiGateway`, `MessagingChannel`, `ApplyConnector`, `InboxConnector`), the shared capability model, call context and normalized error taxonomy. No adapter, no product feature, no deploy. Does not change WP0.2-A's VERIFIED status (PR #9/#10/#11 own that) and does not start WP0.2-B's remaining checkpoint (deployment/CD contract, worker-side correlation), which stays a separate, not-yet-authorized piece of WP0.2-B.

## Context

`docs/IMPLEMENTATION_PLAN.md` WP0.2-B requires canonical interfaces for seven provider-neutral ports before upstream adapter code enters runtime, plus a capability model; `MatchingEngine` remains internal/domain logic and is explicitly excluded from this port set (`docs/SOURCE_REUSE_BLUEPRINT.md` §6 "WP0.2: Create interfaces that upstream code must fit"). `docs/ARCHITECTURE.md` §9/§14 already requires product logic to never call a provider SDK directly and to keep provider abstractions at the ports/adapters boundary. No adapter (Greenhouse, Evolution, an LLM provider, Gmail, an ATS) exists yet, and none is added here.

## Decisions

### 1. `MatchingEngine` is not a port

Unlike the other seven capabilities, `MatchingEngine` has no external provider to abstract: hard filters, lexical/semantic scoring and LLM re-score (`docs/ARCHITECTURE.md` §4) are TapJob's own deterministic + AI-assisted logic, composed from `AiGateway` where an LLM step is actually needed. There is no second implementation to swap in today, so a `Protocol` here would protect a boundary nothing currently needs replaced — exactly the "theoretical abstraction" `docs/ARCHITECTURE.md`'s ports principle warns against. `MatchingEngine` stays internal/domain logic; interface extraction is deferred to WP2.2, and only if a real substitution need appears then (e.g. a second scoring strategy actually being built). `tapjob_api.ports.__all__` never includes it (`test_ports_package.py` asserts this directly), and this checkpoint does not create a `matching_engine.py` module.

### 2. Location: `tapjob_api/ports/`

`services/worker` already depends on `services/api` (`tapjob-worker`'s `pyproject.toml`, ADR-0001 §3: "`tapjob_worker` depends on `tapjob_api` instead of duplicating configuration/logging foundations"), not the other way around. Placing ports inside `tapjob_api` therefore cannot create a circular dependency, and both processes already share this package for their other cross-cutting foundations (`tapjob_api.core.config`, `tapjob_api.core.logging`). A new standalone package would duplicate that already-solved sharing problem for no benefit. `tapjob_api/ports/` mirrors the existing `tapjob_api/core/`, `tapjob_api/http/` pattern: one small package per cross-cutting concern, not a generic plugin framework, not a `ServiceLocator`, not a dependency-injection container — callers import a `Protocol` type and whatever concrete adapter they are given (constructor/parameter injection, nothing more).

### 3. `typing.Protocol`, not `ABC`

Every port is a `typing.Protocol`: structural typing lets a fake (`services/api/tests/test_ports_protocols.py`) or a future donor-derived adapter satisfy a port by shape alone, without inheriting from a TapJob base class. This matters directly for `docs/SOURCE_REUSE_BLUEPRINT.md`: a PORT-classified donor implementation (e.g. JobBot's `JobSource`-shaped adapters, WP2.1) can be reshaped to satisfy `tapjob_api.ports.JobSource` without being forced through an inheritance hierarchy designed around TapJob's own conventions. `ABC` would require every adapter — including a future ported one — to import and subclass a TapJob type merely to be recognized as compliant; `Protocol` needs only the right methods/attributes. None of the Protocols are `@runtime_checkable`: conformance is verified statically, by `mypy --strict` checking that a fake (or future adapter) assigned to a Protocol-typed variable actually satisfies it (`test_ports_protocols.py`'s `_typed_*` assignments) — `runtime_checkable` would only check method *names* exist, not signatures, which is weaker than what the type checker already gives for free.

### 4. Shared primitives, each used only where justified

- **`CallContext`** (`correlation_id` + `deadline: Deadline`): the one cross-cutting concern every port call needs. `Deadline` is an absolute point in time (`Deadline.after(seconds)` / `.remaining_seconds()` / `.is_expired()`), deliberately NOT a retry policy — a port receives one deadline covering the caller's whole operation (including the caller's own retries); the adapter decides, within whatever budget remains, whether/how to attempt the call. No `actor`/generic metadata field was added: nothing in this checkpoint has a real need for it yet (YAGNI), and adding it speculatively would be exactly the kind of "theoretical abstraction" to avoid.
- **`PortError`/`PortErrorCode`**: one exception class, one small code enum (`TIMEOUT`, `UNAVAILABLE`, `RATE_LIMITED`, `AUTH_FAILED`, `INVALID_REQUEST`, `UNSUPPORTED_CAPABILITY`, `OUTCOME_UNKNOWN`, `PROVIDER_ERROR`) — not a subclass hierarchy. `transient: bool` defaults from a code→transience table but can be overridden per-instance when an adapter has better information. `details: Mapping[str, str]` is for already-redacted diagnostics only; raw provider exception text/stack traces/secrets must never reach it (AGENTS.md §8). `OUTCOME_UNKNOWN` is its own code, not folded into `UNAVAILABLE`: "the request may have succeeded but we cannot prove it" is a materially different case from "the provider is down" for a caller deciding whether a side effect already happened (`docs/APPLY_ENGINE.md` §8-9, `ApplyConnector.SubmissionOutcomeStatus.OUTCOME_UNKNOWN` mirrors this at the result level for the one port where it is mandatory).
- **`AdapterHealth`/`AdapterHealthStatus`**: "can we currently reach this provider at all" — distinct from `CapabilityStatus` ("does it support this operation in principle"). Never conflated with `/ready` (ADR-0002), which only probes TapJob's own PostgreSQL/Redis; a future aggregate adapter-health surface, if ever needed, is a separate concern this checkpoint does not build.
- **`ResultMetadata`** (`provider`, `observed_at`, `correlation_id`, `external_ref`, `extra`): small, generic provenance, composed into a result only where a port's result genuinely benefits from it, not forced onto every DTO. `AiResult` instead carries its own richer provenance (`usage`, `safety_status`, `prompt`) because AI results need materially more than the generic shape.

### 5. Capability model: `CapabilityManifest`, a validated container, not a free-function pair

`CapabilityStatus` (`SUPPORTED`, `UNSUPPORTED`, `REQUIRES_PARTNER_ACCESS`, `REQUIRES_USER_ACTION`, `DEGRADED`, `DISABLED`) is the one shared vocabulary (`docs/ARCHITECTURE.md` §5's capability manifest, generalized past booleans). Each port defines its OWN small `StrEnum` of capability keys (`JobSourceCapability`, `MessagingCapability`, ...) rather than one giant enum mixing unrelated boundaries — `docs/ARCHITECTURE.md` §5's own capability manifest already shows unrelated per-provider concepts side by side, which is exactly what a single shared enum would otherwise force. `CapabilityReport[CapabilityT]` is a tiny generic dataclass, not `dict[str, Any]`.

An earlier version of this checkpoint exposed two free functions, `ensure_unique_capabilities` (opt-in validation) and `capability_status_for` (a lookup that did not itself validate). That shape let a duplicate-containing sequence be looked up without ever calling the validator, silently returning whichever report happened to come first — a fail-open bug an independent review caught before merge. The corrected design is `CapabilityManifest[CapabilityT]`: every port's `capabilities()` now returns one, and its `__init__` is the only way to populate it — the same capability key reported twice (even with identical statuses) raises `ValueError` at construction, so no caller can ever end up holding a manifest with a duplicate inside, and there is no separate "remember to validate" step to skip. `status_for()` is the only lookup method and is itself unconditionally deterministic: a capability the adapter never reported resolves to `UNSUPPORTED`, never raising, never `None`, never ambiguous. `reason_for()` mirrors this for the optional `reason_code`. None of this becomes a product feature-flag system (`docs/ENGINEERING_STANDARDS.md` §3.4 already owns that separate concern).

### 6. No SDK/provider/webhook types leak into a port's public surface

Enforced two ways: each port module's docstring states which concrete technologies it must never import (Expo, Evolution/Baileys, Meta WhatsApp, OpenAI/Anthropic SDKs, Gmail SDK, ATS SDKs, browser-extension types), and `test_ports_package.py::test_no_port_module_imports_outside_the_stdlib_and_this_package` parses every `ports/*.py` file's AST and fails if any import comes from outside the standard library or `tapjob_api` itself. `MessagingChannel.ChannelIdentity.external_id` is a plain opaque string (never a Baileys JID shape); `MessagingCapability.FREEFORM_OUTSIDE_SESSION` exists specifically so the WhatsApp Cloud API's 24-hour session-window restriction (which Baileys does not have) can be expressed as a capability difference when that adapter is built, without the Career Core changing (`docs/DELIVERY_ORDER.md` §7).

### 7. `AiGateway`: prompt-delimiting is not, by itself, a security boundary

`AiRequest` separates `variables` (trusted) from `untrusted: tuple[UntrustedContent, ...]` (job descriptions, e-mail bodies, scraped pages — `docs/AI_AGENT.md` §7) and only accepts grounding as `FactRef` (a reference to an already-confirmed `ProfileFact` id, AGENTS.md §6), never a fact value, so a provider's output cannot smuggle in a fabricated "grounded" fact. The module docstring states explicitly that delimiting untrusted content in a prompt is **not**, by itself, sufficient defense against prompt injection (`docs/SECURITY_PRIVACY.md` §7) — it is one input to a layered defense (tool allowlists, structured-output validation, policy checks) that a future caller must still apply; this port does not claim to solve prompt injection alone. `generate` is a generic method (`generate[OutputT](request: AiRequest[OutputT], ctx) -> AiResult[OutputT]`), so each call site gets its own concrete, schema-validated output type rather than an `Any`/`dict` result.

An earlier version of this checkpoint gave `AiRequest` an `output_schema: type[OutputT]` field and let the fake adapter produce `OutputT` by calling it as a zero-argument constructor (`request.output_schema()`) — a shape that proves nothing: it type-checks without ever validating a provider's actual raw response, and a real adapter could do the same, silently returning unvalidated data typed as `OutputT`. The corrected design replaces the field with `validate_output: Callable[[object], OutputT]` — a validator the caller supplies (e.g. a Pydantic model's `model_validate`, wrapped to raise `ValueError` on rejection). `generate()` must call `request.validate_output` on the provider's actual raw response and return exactly what it produces; it must never `cast()` the raw response to `OutputT` and must never construct `OutputT` independently of what the provider returned. A validator rejection is a normal, expected outcome that `generate()` must turn into `PortError(PortErrorCode.PROVIDER_ERROR, ...)` — never let the validator's own exception type escape the port boundary, and never fall back to returning unvalidated data. `test_ports_protocols.py`'s `FakeAiGateway` is built specifically so it cannot bypass `validate_output` by any other path, and is exercised with both a valid and an invalid raw payload.

### 8. `ApplyConnector`: only the `OFFICIAL_API` execution boundary

Of the five canonical modes (AGENTS.md §7), only `OFFICIAL_API` is something a backend adapter itself executes; `ASSISTED_EXTENSION` runs in the browser extension (a future, separate surface), and `DEEP_LINK`/`MANUAL`/`DISABLED` are domain-resolver decisions derived from this port's `capabilities()` plus context this port does not see (e.g. whether a hosted application URL exists at all) — so this Protocol exposes `fetch_form`/`submit`, not one method per mode. `SubmissionRequest.answers` only ever carries `ConfirmedAnswer`s, each with a `confirmation_ref` pointing at the domain's own record of an explicit prior user confirmation (`docs/APPLY_ENGINE.md` §6-7) — this port cannot be used to submit an inferred or guessed sensitive answer; `ConfirmedAnswer.__post_init__` rejects a blank `confirmation_ref` outright (empty or whitespace-only, checked via `.strip()`), since neither can evidence an explicit confirmation. `SubmissionOutcomeStatus.OUTCOME_UNKNOWN` remains mandatory, mirroring `PortErrorCode.OUTCOME_UNKNOWN` at the result level for the one port where "did the side effect actually happen" is a first-class, unavoidable question.

An earlier version of this checkpoint let `SubmissionOutcome(status=SUBMITTED, provider_application_id=None)` be constructed — a caller could read "Applied" off `status` alone with no proof the submission ever reached the provider, directly contradicting `docs/APPLY_ENGINE.md` §10 ("never mark Applied unless submission evidence exists"). The corrected design adds `SubmissionEvidence` (`provider_application_id: str | None`, `provider_receipt_ref: str | None`): each field, when provided, must be non-blank (checked via `.strip()`, so whitespace-only does not count), and at least one of the two must be present and non-blank; and replaces `SubmissionOutcome.provider_application_id` with `evidence: SubmissionEvidence | None`. `SubmissionOutcome.__post_init__` raises `ValueError` if `status is SUBMITTED` and `evidence is None` — the type itself makes a status-without-evidence combination impossible to construct, not merely undocumented. Neither `REJECTED_BY_PROVIDER` nor `OUTCOME_UNKNOWN` requires evidence: a rejection or an ambiguous outcome is not a successful submission, so nothing needs proving and no fake evidence should ever be invented to satisfy the type. `SubmissionEvidence` never carries a raw HTTP body, an auth token/secret, or a provider exception (AGENTS.md §8) — only a stable identifier/reference the domain can later use to look the application up.

### 9. Timestamp normalization: reject naive, normalize to UTC, once

Every normalized timestamp field across the port DTOs (`Deadline.at`, `AdapterHealth.checked_at`, `ResultMetadata.observed_at`, `DiscoveredJob.posted_at`, `JobDetails.fetched_at`, `InboundMessage.received_at`, `SendReceipt.accepted_at`, `InboxMessageSummary.received_at`) applies the same rule (`docs/ENGINEERING_STANDARDS.md` §10): a naive `datetime` is rejected outright at construction (`ValueError`), and an aware-but-non-UTC `datetime` is normalized to UTC, so every normalized port timestamp is directly comparable without a caller re-converting it first. "Aware" is checked per Python's own definition, not merely `tzinfo is not None`: a `tzinfo` object whose `utcoffset(value)` itself returns `None` still makes the datetime naive/ambiguous, and `require_utc_datetime` rejects that case identically to a bare naive datetime (`test_require_utc_datetime_rejects_a_tzinfo_whose_utcoffset_is_none`, with a custom `tzinfo` built specifically to exercise this). The rule lives once, in `_common.py`'s `require_utc_datetime`/`normalize_utc_field`, and every DTO's `__post_init__` calls `normalize_utc_field(self, field_name, optional=...)` rather than re-implementing the check — `Deadline.at` (previously the only field with a bespoke naive-only guard) now goes through the same shared helper as every other port timestamp. `DiscoveredJob.posted_at` is the one optional timestamp (a discovery listing may not report a posting date); `normalize_utc_field(..., optional=True)` leaves `None` untouched instead of raising.

## Testing implications

- Conformance is a static (mypy) check via a typed assignment, not an `isinstance`/`runtime_checkable` check (decision 3).
- `CapabilityManifest` is unit-tested directly (`test_ports_capabilities.py`): unique reports construct and resolve correctly; a duplicate key — same status or different statuses — fails construction; an unreported capability resolves to `UNSUPPORTED`; length/iteration reflect the validated set; there is no path that constructs a manifest holding a duplicate.
- `Deadline`/`CallContext` invariants (timezone-awareness, positive budget, remaining-time arithmetic, expiry boundary) are unit-tested with an injected `now`, not the real clock.
- `PortError.transient` default-vs-override behavior and `OUTCOME_UNKNOWN`'s distinctness are unit-tested directly.
- `FakeAiGateway` is exercised with a valid raw payload (validates into `OutputT`) and an invalid one (normalizes to `PortError(PROVIDER_ERROR)`), proving the fake cannot bypass `validate_output` (`test_ports_protocols.py`).
- `SubmissionOutcome`/`SubmissionEvidence`/`ConfirmedAnswer` invariants (SUBMITTED requires evidence, REJECTED_BY_PROVIDER/OUTCOME_UNKNOWN do not, evidence requires at least one non-blank identifying field -- blank or whitespace-only rejected per field, confirmation_ref rejects blank including whitespace-only) are unit-tested directly (`test_ports_protocols.py`).
- Every hardened timestamp field is unit-tested for naive rejection and non-UTC-to-UTC normalization across every DTO that carries one, plus the optional-field passthrough for `DiscoveredJob.posted_at` (`test_ports_timestamps.py`).
- The AST import-boundary check (decision 6) is itself a test, not just a documentation claim.
- `MatchingEngine`'s absence from the ports barrel is itself an assertion, not just prose.

## Relationship to other decisions

- **Source reuse:** no donor code is imported in this checkpoint. `docs/SOURCE_REUSE_BLUEPRINT.md` §6 names a primary/secondary donor per future adapter (e.g. JobBot for `JobSource`, Basafy for `InboxConnector`); these `Protocol`s are the shape a `PORT`/`ADAPT`-classified donor implementation will need to be reshaped into, so that work can start without first inventing the contract under time pressure. `docs/SOURCE_REUSE_LEDGER.md` is unchanged by this PR (nothing to record).
- **WhatsApp/Evolution:** `MessagingChannel` is the contract `docs/DELIVERY_ORDER.md`'s WhatsApp-first sequencing depends on; Evolution remains a future adapter (WP4.3), not built here.
- **`AiGateway`:** the contract every future AI-touching work package (resume extraction, tailoring, interview prep, inbox classification) must go through (`docs/ARCHITECTURE.md` §9); no provider is selected or implemented here (OQ-040 stays open).
- **`ApplyConnector`:** aligns with the already-Accepted five apply modes (D-010) and the failure taxonomy in `docs/APPLY_ENGINE.md` §9, without re-opening either.

## Consequences

- Seven small modules plus two shared-primitive modules, each independently reviewable; no framework, no generic plugin system, no DI container was introduced.
- `ApplyMode` (the five-value enum) is defined in `ports/apply_connector.py` for now, since no domain/enums package exists yet (WP0.1-WP0.2 explicitly ship no domain models) — a reasonable, documented provisional home. It may move to a dedicated domain module once WP5.1 or an earlier work package introduces one; that move is a mechanical relocation, not a contract change.
- Every DTO here is provisional and intentionally minimal (job_source.py, resume_parser.py, resume_renderer.py especially): the owning work package (WP2.1, WP1.3, WP3.1) may extend them once a real adapter's actual needs are known, via a documented decision — not silently, and not by guessing ahead of real requirements.
- `MatchingEngine` staying out of this port set means WP2.2 starts from a clean slate on whether it ever needs a `Protocol` at all; this ADR does not pre-decide that.
